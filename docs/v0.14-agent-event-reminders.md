# v0.14 阶段 B · 事项提醒

## 数据与时间规则

单项规则继续存于 SQLite 或旧 JSON 的 `native_reminders.events[Event ID]`。SQLite 表结构、全局偏好与通知台账格式沿用现有版本。

| 模式 | 持久化与计算 |
|---|---|
| Default | 显式存 `{"mode":"default"}` 并清空旧 `Event.reminder`。普通、紧急事项以首个有效日期为锚，DDL 和末日 DDL 以最后一个有效日期为锚，使用现有全局提前天数和默认钟点。无覆盖的历史定时事项仍按原分钟值运行。 |
| Relative | `minutes` 支持 0–10,080，要求已有开始或截止时刻。定时分钟值继续同时保存在旧字段。按天支持 0–365 天，可指定钟点；省略时沿用明确的开始或截止钟点，全天事项使用默认提醒钟点。沿用旧 `custom` 规则。 |
| Absolute | `at` 存本地日期时间 `YYYY-MM-DDTHH:MM`。普通改期、批量平移和撤销保留这个固定值。编译只调整钟点的请求时优先保留已有计划日期，无计划时使用事项锚点。 |
| Disabled | 沿用 `{"mode":"off"}`，清除旧提前分钟值。恢复默认替换关闭或自定义规则。 |

稍后提醒仍由独立台账保存，规则改期只使旧计划和相关稍后状态按原引擎规则失效。绝对时间的计划键不随事项改期更换，避免同一固定提醒因改期重新派发。通知时钟使用本机时间，Agent 的相对日期按当前消息的时间锚点解释。

## Operation Plan 和事务

`propose_events` 的 `fields.reminder_rule` 接受 `default`、`relative`、`absolute`、`disabled`。Relative 使用 `minutes` 或 `days`（后者可带钟点）。Absolute 使用 `at`，只改提醒钟点时可传 `time`。单项提案保留旧 `reminder` 输入，两种输入不能同时给出。纯提醒修改可以按精确标题定位，多个候选仍需选择。普通事项修改省略此字段，从命令前态继承规则。

Event 命令快照包含原始规则值。确认核对 Event、有效日期、规则快照及预览过的提醒结果。原规则或事项改变会使旧计划失效，外部 SQLite 写入另受仓库 Revision 保护。批量修改依然只生成一个命令。SQLite 复用同一事务更新 Event、通知键、局部偏好及操作回执。JSON 复用原单文件保存及恢复路径。

操作结果分开核对事务、规则及计算后的触发时间。提交后重建计划，不派发通知。失败时保持引擎待重算，当前回执明确提示，后续本地 tick 或重启重建。撤销保留送达台账并恢复规则，已发送的通知不能撤回。远程继续复用原有文本和引用撤销，`remote-interaction-v1` 仅在 `reply_text` 增加提醒细节。

阶段 C 可直接复用注入 Calendar Runtime 的同一 `ReminderEngine`、`CalendarActionGateway.detail` 的提醒投影、`ReminderEngine.overview` 的只读计划和现有计划键。阶段 B 未接入提醒计划列表和稍后提醒 Agent 指令。
