# v0.14.0 主动通知共享协议提案

## 提交接口

| 字段 | 约定 |
| --- | --- |
| 入口 | `POST /api/notifications/proactive` |
| 认证 | 沿用 HTTPS 服务根地址和 `X-Worker-Token`。Token 由已核验的 Worker 绑定提供 |
| 账号 | 服务端将 Token 映射到内部账号，逐请求比对 `account_id`，再解析该账号当前有效的 QQ 绑定 |
| 幂等键 | 当前服务器上由 `account_id`、`channel` 和 `notification_id` 组成 |
| 有效期 | `triggered_at`、`expires_at` 为包含 UTC 偏移的 ISO 8601 时间。服务端比对当前时间并拒绝过期消息 |
| 结果 | 成功响应必须为 HTTP 200，包含相同的 `account_id`、`channel`、`notification_id` 和最终状态 |
| 业务类型 | `event`、`ddl`、`brief`、`test` |
| 渠道 | 此接口以 `qq` 联调，Windows 保持本机分发 |

```json
{
  "protocol_version": 1,
  "notification_id": "7af9bcbfafb4135389be6115858119d455e47db177acb7ba6830a599ae6d98e4e",
  "type": "event",
  "account_id": "sample-internal-account",
  "channel": "qq",
  "triggered_at": "2026-11-25T21:25:00+08:00",
  "expires_at": "2026-11-26T21:25:00+08:00",
  "private": false,
  "count": 2,
  "items": [
    {"index": 1, "title": "复核项目资料"},
    {"index": 2, "title": "发出会议议程"}
  ],
  "fallback_text": "复核项目资料\n发出会议议程",
  "actions": []
}
```

简报的事项可以带 `group`、`time`、`date`。分组为 `timed`、`untimed`、`unfinished`、`upcoming`、`overdue`。QQ 只收到要发送的当次通知，事项内部 ID、备注、资料路径和历史留在本机。隐私启用时 `items` 为空，`fallback_text` 仅含必要通用信息，交互在可用时最多允许「知道了」。QQ Markdown 必须转义事项文本，遇到模版、渠道版本或能力限制后直接使用兜底文本。

```json
{
  "notification_id": "7af9bcbfafb4135389be6115858119d455e47db177acb7ba6830a599ae6d98e4e",
  "account_id": "sample-internal-account",
  "channel": "qq",
  "status": "sent"
}
```

- `sent` 表示 QQ 发送 API 已确认。服务端需要持久化此决定，重复请求返回原状态并保留实际消息标识。
- `failed` 表示确认此次未向 QQ 发送。客户端可在有效期内等待 2 分钟后有限重试，最多 3 次。明确失败后重试可带最新的有效成员及脱敏内容。
- `unknown` 表示已到达可能产生副作用的边界。幂等记录持久化为待核查，重复请求返回已有状态。网络中断、无法匹配身份的回执和含发送歧义的响应对客户端具有同样语义。
- HTTP `400/401/403/404/413/422/429` 仅用于明确拒绝且尚未发生 QQ 发送的情况。发送边界后的异常应返回 `unknown`，或用服务端可核验的现有幂等结果回应。
- 测试通知使用独立 32 位十六进制 ID，其他通知使用 64 位十六进制 ID。服务端 DB 或队列需要容纳 20 项聚合，较长内容可在渠道展示层摘要，同时保留实际总数。

## 动作回流及 v0.13.1 依赖

当前客户端按纯文本降级，行为与 v0.13.1 中 `interaction_schema_version` 的思路一致。待 v0.13.1 的原生 QQ 路由、内部账号字段、已发消息引用和结构化动作就绪，建议按现有会话能力协商增加主动通知能力字段。只有本机及当前账号路由共同支持的动作才能进入 `actions`，其中 `target` 为本机批次 ID。

| 场景 | 动作 | 含义 |
| --- | --- | --- |
| 日程、DDL | `acknowledge` | 在 QQ 通道记录「知道了」。事项完成状态由日历操作维护 |
| 日程、DDL | `view_items` | 从同一批次读取仍有效的事项 |
| 日程、DDL | `snooze_10m` | 按钮明确标成「本通知中的有效事项，10 分钟后提醒」，作用到该批次仍有效的原提醒 |
| 简报 | `view_today`、`view_week`、`view_ddl` | 复用稳定后的结构化快捷查询，按点击时的本地日历返回结果 |

Antigravity 侧将云端生成的不可预测 `action_id` 与原消息、机器人应用、QQ 对话、内部账号、通知 ID、动作和有效期绑定。收到按钮点击时核验上述归属及调用人，使用稳定点击 MsgId 进入现有 claim/complete 流程。本机适配器复用 v0.13.1 原生路由与动作幂等，使用 `apply_qq_action` 在日历线程处理已实现的日程动作。简报查询适配等待 v0.13.1 的快捷查询接口。账号及 Worker Token 换绑后，旧批次冻结到原归属，旧排队项不迁往新账号。

## Antigravity 配合事项

1. 上线并联调认证、幂等和最终回执接口，确认 QQ 主动发送权限、平台限流及过期处理。
2. 连续发送同一幂等键、注入发前拒绝与发后丢回执，核对渠道仅发送一次。模拟 Token 吊销及不同账号重新绑定。
3. 先验证纯文本和隐私负载，再协商 QQ Markdown、按钮能力与动作回流。简报快捷查询沿用 v0.13.1 稳定后的接口。
4. 用合成账号分别验证 Windows、QQ 部分失败和 20 项聚合。只有客户端当次到期后才提交有效内容，在线调度仍归本机。

### 手动试发简报

测试复用简报载荷，额外带可选布尔字段 `is_test: true`，纯文本兜底以「【测试简报】」开头，动作数组为空。客户端生成独立通知 ID；服务端若使用结构化模板，应保留测试标记，试发与每日简报去重分别处理。真实 QQ 接口支持仍待联调。
