# Schema 7 / 8 更新交接回归

## 已确认根因

v0.9.1 主程序与其更新器支持数据 Schema 7；v0.9.2 的习惯周期使用 Schema 8。源码运行与打包 EXE 默认共用 `%APPDATA%/DesktopCalendar`。
较新源码保存 Schema 8 后，旧 EXE 会先宽松读取，随后将其当成“需要迁移”的数据。在保存前，旧的备份验证器拒绝 Schema 8。
旧交接顺序为 `launch_updater -> Store.save -> schedule exit`，因此保存失败后没有安排退出，进度窗停在启动更新器阶段，更新器只能等待或超时。
错误来源是正常 JSON 的迁移前备份验证，不是一个已经损坏的备份 ZIP。保留拒绝不兼容写入的保护，不能改低版本或忽略校验。

## 修复边界

- 共享只读 Schema gate；Store 在解析前以及每次保存前拒绝未知较新 Schema。加载失败时禁止保存，不打开可编辑的空日历。
- Schema 8、备份容器格式 1 均不变化。支持旧 Schema 的正常迁移，迁移前保护原字节。
- 区分数据格式损坏、Schema 过新、权限问题、备份容器版本不兼容、更新未完成。拒绝写入不等于声称整个升级从未修改过数据。
- 交接改为先保存，再从已校验的 ZIP 暂存新版更新器，最后安排退出；交接退出不再保存第二次。保存或启动失败清理进度 UI，并保持主程序可用。
- 更新器仍等待指定 PID；访问被拒、等待失败或另一个单实例存在时失败关闭，不杀任何用户进程。
- 更新器在备份和复制前取得安装互斥，并同时持有原有 App 单实例互斥名：已发布旧程序也不能在复制途中进入数据。释放所有保护句柄后，才从指定安装目录重启，不执行数据恢复。新版启动还会明确提示更新尚未完成。
- 修复工具与普通更新共享同一个 ZIP 更新器暂存 helper，避免两套提取实现漂移。

## 使用与发布

v0.9.2 已公开，不能改写其 tag/资产。此修复留待新的 Hotfix 发布。已经安装的旧 EXE 不会因源码提交而改变：退出旧版，使用新版修复工具或解压新版至新目录后启动；不需要删除个人日历。
开发/GUI 验证必须使用显式隔离的 APPDATA，参考 README。全局单实例约束仍保留。

`tests/test_update_compatibility.py` 使用合成记录和真实 v0.9.1 tag 源码验证旧读者失败路径；不能将模拟 Schema gate 的测试当成旧版二进制已修复。
`tools/check_update_compatibility.py` 可在临时安装和合成 APPDATA 上验证已发布 ZIP 启动、Schema 迁移、拒绝未来数据、新更新器等待/复制/重启及四主题焦点。
测试可结束自己直接创建并核对临时路径的 QA 进程，绝不用于真实用户进程。QA 构建不是正式 Release；正式发布仍需单独授权。

## 剩余限制

旧公开版本无法热修补，必须换用兼容程序。更新文件复制仍为逐文件复制，不是整个安装目录的事务回滚；复制异常时不重启、不恢复或修改日历，程序文件可能需要独立修复工具重新安装。
安装互斥覆盖遵守原有 SingleInstance 协议的新旧版本，但不能控制绕开该协议的外部程序。若复制期间手工打开很旧的版本，其“已在运行”提示可能暂时持有单实例句柄，需先关闭提示再启动兼容版本；数据读取仍被阻止。数据写入边界仍需 Schema gate 保护。
