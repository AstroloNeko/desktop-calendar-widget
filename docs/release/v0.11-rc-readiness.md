Open, causing repeated missing-file warnings on the user's screen. That was a QA
script defect, not evidence of database corruption. The isolated test was stopped.

known migration confirmations receive at most one action per HWND/content, with

generate no native input. Backup ZIPs passed to the updater are now private copies
(the updater legitimately consumes its input on success). QA SQLite readers use
explicit connection closing; a test-only cleanup failure was fixed and rerun.

The frozen RC updater was actually invoked against a synthetic ACTIVE profile
with the old v0.10.2 ZIP. It returned failure **before copy/restart**; destination
sentinel and storage-state bytes were unchanged. Exactly one error acknowledgment

failure, failed protection/restore, process lease contention and interruption.

atomicity is not claimed; failed copying may still require Repair.

## Production enablement and retention

- Default normal launch remains non-migrating. Explicit
  `DesktopCalendar.exe --upgrade-storage` displays consent before migration.
- New profiles initialize via the existing default serializer only after consent;
  existing Schema8/9 profiles use strict conversion. Cancel retains JSON; ACTIVE
  corruption refuses rather than initializes or falls back.
- No global flag or configuration needs to be flipped for this opt-in entry.
  A default-on rollout/menu shortcut is a separate release decision, not silently
  enabled by building RC. After activation, ordinary launch selects SQL.
- Protection: `original-<epoch>.json`, old DBs, stage reports and
  `disaster-original-<epoch>` are retained in the profile. Regular backups are in
  `backups`; none of this work adds cleanup or deletes the last good copy.
- Conservative no-pruning avoids unsafe rotation but can consume disk (P1).
  Recovery is accessible through `--recover-storage`; normal data-management UI
  handles readable databases. Reminder replay risk is explicitly accepted in
  restore consent; an old backup may resend a previously delivered reminder.
