## 旧版触发链与复现

`CalendarApp.check_reminders` 经 Tk 根窗口的 `after` 执行 `NativeReminderMixin._native_reminders_tick`。旧引擎使用 `plans_for_store` 构建堆，预留逐事项状态后，把请求放入 Windows 后端线程。WinRT 返回经线程队列交回 Tk。提醒计划从同一规则及 SQLite/JSON 设置计算只读投影。单事项自定义规则优先，显式关闭或有具体时间且未选提前量时跳过。习惯走 `due_routine_reminders`、`Store.notified` 和 Tk 习惯弹窗。

在真实 Windows Tk 上创建 8 项合成普通事项，时间固定到 2026-11-25 21:25。提醒计划窗口保持打开并持有模态输入，通知传输用探针替换，时钟注入旧引擎。第一轮从 0 条提交进入 3 条提交，余下 5 项保持等待。+15、+60、+120、+299 秒仍只有 3 次入队。+300 秒再次出现调度，探针随后故意不回执，+600 秒累计入队混有重试。由此确认旧引擎的每轮 3 项和持久化每 5 分钟 3 项限制会让 8 项分批滞留。旧后台回调在首轮习惯提醒、持久化或渲染抛异常时也会跳过末尾的 `after`，后续日程轮询因此可能中止。旧通知动作与模态窗口有阻塞判定，通知发送路径和模态输入抓取没有这一判定。

原现场 21:25 的第一屏显示 0 次提交。旧调度有最多约 15 秒的轮询等待，加上 Windows 后端异步初始化和回执延迟。现有记录无法确定原现场第一屏属于轮询等待、异常中断还是系统通知延迟。Windows Tk 的合成复现期间，模态输入本身允许定时回调执行。

## 保留、重构与新增

| 模块 | 变更 |
| --- | --- |
| `reminder_engine.py` | 保留规则、有效日期、事项稳定标识、逐事项关闭、旧通知与稍后记录的导入。新增批量稍后提醒和新版回执入口 |
| `notification_dispatch.py` | 按本地分钟及业务类别选择全部到期事项。所有通道的发送预留先持久化，再独立入队 |
| `notification_model.py` | 定义业务通知、Windows 摘要、简报分组和排序 |
| `notification_backend.py` | 复用 WinRT DLL、可执行文件与数据目录绑定的 Windows 注册、异步提交与激活 |
| `qq_reminders.py` | 复用已核验 Worker Token 和 HTTPS 请求。提交和回执独立于 Windows |
| `sqlite_calendar_repository.py` | 提醒只提交一个设置键，复用现有的 revision、原子事务和提交凭证。JSON 保留原保存链路 |
| `reminder_ui.py`、`reminder_center.py`、`reminder_overview.py` | 统一窗口的四个选项卡、实时状态、失败详情、通知明细和单事项操作 |
| `app.py` | 根窗口每 2 秒检查日程，原习惯提醒每 15 秒独立检查。两条计时回调均有下次调度保证 |

普通、紧急事项合并到日程组，DDL 单独合并。已计划在同一分钟的秒级触发最多等到该组最后一个触发点。恢复运行时可将超过一分钟的有效积压按业务类别合并，过期上限沿用 24 小时。批次成员关联到各自原计划，保留完成、改期、删除和稍后的业务状态。Windows 显示最多 3 条摘要和总数，点击通知打开第四栏查看完整成员。单项 Windows 通知沿用原有打开事项及 10/30/60 分钟稍后操作。

状态记录按通道保存。到点前为等待触发，预留后为待发送或等待结果，完成后呈现 Windows 已提交、QQ 发送成功、明确失败、结果不确定、过期或取消。Windows 系统回执记录 WinRT 提交，QQ 成功记录渠道 API 结果。两条链路均没有已读证明。明确失败至多 3 次，每次间隔至少 2 分钟。未收到可信回执或进程在预留后退出，状态变为不确定，暂停重发。旧 `accepted` 与旧已知提醒键继续去重，旧 `dispatching` 在首次处理时保守迁为不确定。

每日简报默认关闭，默认时刻 08:00，补发到当天原时刻后的 4 小时且以午夜为上限。简报使用当前 Store 的本地 SQLite 日历快照，分组按当天定时、当天全天、当天未完成、近期 DDL、逾期 DDL 依次取第一个已启用的匹配组。Windows 以本机日历与日期去重，QQ 以已核验服务器、内部账号与本地日期去重。无事项时默认记录跳过。新用户设定启用后仍可独立选择 Windows 或 QQ。

Tk 保持权威 Store 的写入所有权。Windows 和 HTTPS 调用在各自工作线程，回执经队列回到主线程。SQLite 的短预留和回执事务留在主线程，由 SQLite 的现有忙等待上限约束。大量长期历史仍会累积，真实验收为下述规模。
